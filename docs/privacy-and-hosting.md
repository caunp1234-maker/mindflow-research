# 개인정보 취급 원칙 · 호스팅

## 1. 개인정보 최소화

- 코딩·내보내기·대시보드 목록 등 다수가 보는 화면은 기본적으로 `screeningNumber` + `initials`만
  노출한다(PDF 표지의 "스크리닝 번호 / 대상자 이니셜" 관례를 그대로 따름, `data-model.md` §4).
- 실명(`Subject.name`)·연락처(`Subject.contactPhone`)·인구통계 상세는 별도 권한이 있어야 열람 가능한
  "피험자 상세" 화면에만 노출한다.
- 결과보고서·연구 결과 활용 시 "참여자의 개인정보가 확인되지 않도록 처리"한다는 원칙은 슬라이드 8의
  임상척도 안내문에 이미 연구팀이 참여자에게 공지한 내용이므로, 시스템 설계도 이를 준수해야 한다.

## 2. 파일 보관 (결정 #3)

신분증 사본·통장사본·가족관계증명서는 **기존 보관 경로에 그대로 둔다.** 앱은 `IdDocRef`
(`data-model.md` §4-1)로 문서 종류·제출 여부·제출일과, 실제 위치를 가리키는 설명 텍스트만 가진다.
앱 DB에 파일을 업로드하는 기능 자체를 만들지 않는다 — 업로드 폼, 파일 스토리지, 접근 URL 모두
Phase 1–5 범위에서 제외한다.

결과보고서 PDF(Phase 5, SSD_CBT는 비대상)에 대해서도 같은 원칙 적용을 검토한다 — 생성된 보고서를
DB에 영구 저장할지, 아니면 즉시 다운로드 후 폐기하고 메타데이터만 남길지는 Phase 5 착수 시 다시
결정한다.

## 3. 저장 데이터 암호화 · 접근 통제

- `Subject.name`, `contactPhone`, `demographics`(생년월일 포함) 등 식별 가능 정보는 DB 컬럼 단위
  암호화(at-rest)를 기본으로 한다.
- 역할 기반 접근 통제(`data-model.md` §9):
  - `researcher`(연구원): 담당 연구의 피험자 전체 정보 CRUD
  - `pi`(교수님): 슬라이드 21–23이 요구하는 "인롤 현황 대시보드"(연구별 타임라인, 목표 N 대비 등록
    현황) — **PII 전체 접근 범위인지 익명화된 현황 수치만인지는 미확정**(`open-questions.md`)
  - `admin`: 계정·권한 관리
- 모든 PII 조회·수정은 `AuditLog`에 기록한다.

## 4. 보관 기간

연구 종료 후 데이터 보관·파기 기간은 IRB 승인 문서(SSD_CBT IRB 서류)에 규정돼 있을 가능성이 높으나,
이번에 확보한 두 문서(설문지 PDF, PHQ.docx)에는 명시돼 있지 않다. Phase 1 착수 전 IRB 서류에서
보관기간 조항을 확인해 `AuditLog`/백업 정책에 반영해야 한다.

## 5. 호스팅 (미확정)

병원 임상연구 데이터이므로 원칙적으로 **국내 소재 인프라**(사내 서버 또는 국내 클라우드 리전)를
전제로 설계한다 — 이는 확정이 아니라 안전한 기본 가정이며, 실제 배포 환경(사내 온프레미스 서버 vs
관리형 클라우드 VM)은 사용자 확인이 필요하다(`open-questions.md`). 스택은 Node.js + PostgreSQL로
확정됐으므로(결정 #1), 온프레미스든 클라우드든 동일한 구성으로 이식 가능하게 설계한다(컨테이너화,
환경변수 기반 설정).
